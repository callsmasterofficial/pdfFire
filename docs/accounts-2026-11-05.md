## Why the password hashing is split

This is the one design decision here worth explaining, because it looks unusual.

Measured in workerd, the engine Pages Functions actually run on:

| PBKDF2-SHA256 | cost |
|---|---|
| 10,000 iterations | 1 ms |
| 50,000 | 6 ms |
| 100,000 | 9 ms |
| **210,000** (OWASP's current recommendation) | **17 ms** |
| 600,000 | 59 ms |

The Workers free plan allows **10 ms of CPU per request**. The recommended cost
does not fit, and 100,000 spends the entire budget on the hash with nothing
left to answer with.

So the expensive derivation runs in the browser — 600,000 iterations, free, and
nobody else is waiting — and the edge stretches the result again at 10,000,
costing about 1 ms. An attacker holding the database still has to work back
through the client-side derivation to reach a password, so the offline cost is
kept rather than traded away.

This follows Mozilla's onepw protocol. It is not an invention of this codebase,
which matters: a bespoke authentication scheme is exactly the kind of thing
that looks fine and is not.

What the server receives is password-equivalent in transit, exactly as a plain
password would be, and is protected the same way — TLS, and never logged.

The alternative is the paid Workers plan, which raises the limit to 30 s and
would allow the whole derivation server-side. That is a cost decision, recorded
here rather than taken quietly.

## Verified against a real database

Driven end to end through the real protocol, including the client-side
derivation, against D1:

| | |
|---|---|
| session before anything | `200 {"account":null}` |
| register | `201` with the account |
| session after register | authenticated |
| duplicate register | `409` |
| derivation below the required cost | `400` |
| logout | `200`, session cleared |
| wrong password | `401` |
| unknown address | `401`, **the same message** |
| correct password | `200`, same account id |

Wrong password and unknown address return an identical message, so the endpoint
cannot be used to discover which addresses are registered.

Rate limiting, exercised rather than assumed: five wrong attempts return `401`,
the sixth returns `429`, and a *correct* password during the lockout also
returns `429` — the limit is on the address, not on being wrong.

**Registration is limited too**, which it was not at first. The client-side
derivation does not help there: an attacker writes their own client and sends
a well-formed auth key without doing the work, so an unlimited public
registration endpoint is an invitation to fill the table. Five per address per
hour, counted on `CF-Connecting-IP`, which the edge sets and a client cannot
forge. The counter is shared with sign-in but prefixed — `login:<email>` and
`signup:<ip>` — so neither can exhaust the other's budget.

What is actually stored was read back out:

```
password_hash  55f97db9f23936df60e38902...  (64 hex, a PBKDF2 output)
password_salt  2a293556c99e7dc854f185bedc0d87c6   (per row)
iterations     server 10000, client 600000        (per row, so cost can rise)
session        token_hash 854e5d53...             (never the token)
```

## What this does not do

- **No email verification, and no password reset.** Nothing here can send
  email. Claiming an address is verified would be false, so `emailVerified` is
  always `false` and is reported that way to the client. A reset flow needs an
  email provider; that is the next real dependency and it is the one genuine
  candidate for an external service — see the AWS note below.
- **Entitlement enforcement.** See below; it is the next piece.
- **No entitlement enforcement yet.** Accounts exist; nothing reads them to
  decide what a user may do. That is the next piece, and it does not need Dodo
  either.
- **No Teams roles or seats.** The schema has `organizations`, `memberships`
  and `invitations`; nothing writes to them yet.
- **`auth_attempts` is not pruned** except on a successful sign-in. An address
  that only ever fails, and every registration, leaves a row behind. Harmless
  at this size, worth a scheduled cleanup before it is not.

## On AWS

Still nothing requires it. Storage is D1, compute is Pages Functions, both on
the existing Cloudflare account. The one thing the product now visibly lacks —
sending email for verification and password reset — could use SES, but Resend,
Postmark and Cloudflare's own email routing are all closer to hand and none of
them pulls in an AWS account. Recorded separately as the brief asks: **no
genuine AWS requirement has appeared.**
